# Navideck — project instructions

## Start from the current GitHub state

The local checkout can lag behind `origin/main`. Run `git fetch` and check
`git log --oneline HEAD..origin/main` before changing code. Never force-push
`main` or replace newer remote work with a stale tree.

## Keep every platform in step

Navideck ships from one repository in three shapes:

- **Web** — `src/` (React + Vite), served by the container/PWA
- **Windows/Linux** — `desktop/` (Electron, packages the web build)
- **iOS** — `ios/` (native SwiftUI app, own Subsonic client and player)

The app is under active development. Every behaviour change, new feature and
bug fix must be applied to **all versions it affects** in the same piece of
work — never only to the web app or only to iOS. UI work is adapted to each
platform's idiom, but features, API calls, labels and behaviour stay aligned.
If a change genuinely cannot be ported yet, say so explicitly in the final
answer and record it in `ios/README.md` (or the desktop notes).

## Always publish to GitHub

After every completed change, commit the relevant files and push `main`. The
`Build image` workflow then publishes `ghcr.io/senar030/navideck:latest`; the
user redeploys that image in Portainer. Mention in the final answer that a
redeploy is possible once the workflow has finished.

## Always ship a desktop release

Every completed user-facing change also gets a desktop release:

1. Bump the version in `desktop/package.json` (minor for features, patch for fixes).
2. Update `desktop/RELEASE_NOTES.md` (German, what changed + installation notes).
3. Commit and push `main`.
4. Create and push the tag `desktop-v<version>`.
5. Wait for the `Desktop release` workflow. It builds
   - `Navideck-Setup-<version>.exe` (Windows, NSIS)
   - `Navideck-<version>-x86_64.AppImage` (Linux, x64, for Bazzite)
   and publishes both as a GitHub release.
6. Download the assets into the local `release/` folder:
   `node scripts/fetch-desktop-release.mjs <version>`.
7. Report the release URL and local file paths.

Do not commit `release/` — it only holds downloaded build artifacts.

## iOS releases

The native app lives in `ios/` (SwiftUI; the Xcode project is generated by
XcodeGen). The repository sits in a cloud-synced folder, and Xcode writing into
`ios/Navideck.xcodeproj` made Nextcloud create duplicates and delete
`project.pbxproj`. Never generate or build the project inside `ios/`; work on a
local copy instead:

```bash
node scripts/ios-workdir.mjs --open   # -> ~/Developer/navideck-ios
```

Local signing team: `.ios-team` in the repo root or `NAVIDECK_TEAM` (neither is
committed).

Every user-facing iOS change:

1. Bump `MARKETING_VERSION` in `ios/project.yml`; the workdir script picks it up.
2. Update `ios/README.md` when the feature set changes.
3. Commit and push `main`.
4. Tag `ios-v<version>` and push the tag. The **iOS build** workflow builds an
   unsigned IPA and publishes it as a GitHub release.

The IPA is unsigned: the user signs it with Sideloadly or AltStore. Mention the
release or artifact link in the final answer.

## Desktop packaging

The Electron wrapper lives in `desktop/` (`main.cjs`, `package.json` with the
electron-builder config). The web app is built first (`npm run build`), then
packaged. Linux is an AppImage so it runs on Bazzite without system installation.
